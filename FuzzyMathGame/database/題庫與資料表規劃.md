# FuzzyMathGame 題庫與資料表規劃

日期：2026-10-20。這份是待實作設計，不代表 MySQL 已建表或題庫已完成。題型規劃.csv 為完整章節目錄；第 2–8 章代碼是本次提案，匯入同學資料前仍須比對。

## 1. 現況與目標

目前遊戲以 local_questions.py 的四個練習題型運作；題目尚未存進資料庫。正式 calculation_engine.py 已有 F01–F20 的答案計算程式，但這不等於有題目模板、五級難度、完整步驟或選項資料。本機 MySQL 先前檢查沒有 fuzzy_math_game，尚未拿到同學原始 SQL。

目標是儲存「題型＋難度規格＋參數＋解題步驟＋錯誤選項規則」，產生很多合理的題目，不預存大量只有數字不同的題目。Fuzzy 決定難度，資料庫提供已發布的規格；沒有該級別時應明確回報，不悄悄改難度。

## 2. 題型編號先對齊

## 3. 完整內容範圍與難度

完整章節包含函數基礎、極限、微分概念、微分法則、微分應用、不定積分、定積分及積分應用，詳見 CSV。第一章 20 題族是程式既有分類，其餘 30 題族為提案，共 50 題族；不是承諾一次完成 250 個難度規格。

難度不只改大數字：1 基本正整數與直接規則；2 加入負數、常數或一層代入；3 多項運算、分數或一個概念陷阱；4 多法則組合與條件判斷；5 綜合應用與特殊情況。每級需寫具體規則、示例和限制，不能只套通用說明。難度先人工規劃，再由老師確認；累積作答資料後才評估調整。

每個規格的必填內容：學習目標、來源、題目文字與 LaTeX、參數範圍、跨參數限制、答案規則、逐步推導、每步提示、三種錯誤觀念、標準示例、預期時間、審核狀態。

## 4. 資料表與關係

保留正式 app.py 已查詢的七張表；目前沒有原始 DDL，以下型別為建議，取得原始 SQL 後以實際欄位及主鍵型別為準。遷移前比對 SHOW CREATE TABLE，禁止直接套用新型別或重建既有表。

| 表 | 主要欄位與建議型別 | 約束與用途 |
|---|---|---|
| chapter（新增） | chapter TINYINT、name VARCHAR(100)、display_order SMALLINT | chapter 主鍵；八章目錄 |
| question_type | type_id VARCHAR(16)、chapter TINYINT、name VARCHAR(100)、description TEXT、status VARCHAR(16) | type_id 主鍵，chapter 外鍵；狀態 draft/published/archived |
| question_spec | spec_id VARCHAR(64)、type_id VARCHAR(16)、difficulty TINYINT、question_template TEXT、question_latex_template TEXT、answer_rule VARCHAR(100)、expected_seconds SMALLINT、status VARCHAR(16)、source_note TEXT、version INT | spec_id 主鍵；type_id 外鍵；現有查詢 LIMIT 1 無版本排序，因此第一階段 UNIQUE(type_id,difficulty)，版本先存修訂紀錄，不並存多個同級版本 |
| parameter_definition | parameter_code VARCHAR(32)、data_type VARCHAR(24)、default_min DECIMAL(18,6)、default_max DECIMAL(18,6)、allow_zero BOOLEAN | parameter_code 主鍵；共用整數、非零整數等型別 |
| spec_parameter | spec_id、parameter_name VARCHAR(32)、parameter_code、min_value/max_value DECIMAL(18,6)、excluded_values JSON、constraint_rule TEXT | (spec_id,parameter_name) 複合主鍵；兩個外鍵；上下界、排除值及單一參數限制 |
| generation_rule | rule_id BIGINT、spec_id、rule_code VARCHAR(64)、rule_config JSON、description TEXT | rule_id 主鍵，spec_id 外鍵；跨參數限制，例如分母不為零、兩點 x 不同。現有後端尚未實際讀取，必須補上才會生效 |
| solution_step | step_id BIGINT、spec_id、step_order SMALLINT、step_template TEXT、step_latex_template TEXT、step_description TEXT、hint TEXT、answer_template TEXT | step_id 主鍵；UNIQUE(spec_id,step_order)，順序連續從 1 開始；spec_id 外鍵 |
| solution_option（新增） | option_id BIGINT、step_id BIGINT、option_order TINYINT、text_template TEXT、latex_template TEXT、value_rule VARCHAR(100)、rule_config JSON、is_correct BOOLEAN、misconception_code VARCHAR(64)、explanation TEXT | option_id 主鍵；step_id 外鍵；UNIQUE(step_id,option_order)，候選規則先經產生器挑選四個有效選項 |
| blank_rule | blank_id BIGINT、spec_id、step_order SMALLINT、blank_key VARCHAR(32)、target_expression TEXT、correct_answer_template TEXT、answer_type VARCHAR(24)、blank_level TINYINT、hint TEXT | 保留原填空版相容用途；UNIQUE(spec_id,step_order,blank_key)，(spec_id,step_order) 對應 solution_step；四扇門不強迫使用挖空 |

所有文字 utf8mb4，交易表 InnoDB。題目難度限制 1–5，步驟與版本正整數，參數 min<=max。子表索引涵蓋 spec_id、step_id；不對已被作答紀錄引用的題型做實體刪除，改 archived。建立時間與更新時間使用統一 UTC 儲存。

「每步恰好四個選項且恰好一個正解」屬跨列約束，不能只靠一般 CHECK；在題庫發布交易及每次產題時共同驗證。規則候選可以超過三個錯解，以便某組參數造成答案相同時換其他錯解；API 最終必須只回四個不同、恰好一個正解的選項。

## 5. 四扇門資料範例

正式 F09／難度 1，規則 LINEAR_EQUATION_BASIC（參數名必須依答案引擎要求比對）。示例 3x+4=10，標準答案 x=2。

步驟 1：兩邊減 4，右邊 10−4=6。錯解 14（移項忘記變號）、7 或 5（計算偏差）。
步驟 2：兩邊除 3，x=6÷3=2。錯解 18（乘除顛倒）、3（把除法當減法）、1（計算偏差）。

先存錯誤規則及觀念，再用題目參數生成數字；不把其他正確解題步驟標成錯誤。若同題有另一種有效解法，題幹須限定目前路徑，或重新設計錯誤選項。不得用一般文字如「重新檢查」充當數學錯解。

## 6. 出題、驗證與作答紀錄

流程：章節可用題型 → Fuzzy 選難度 → 選已發布規格 → 有界重抽參數並驗證全部限制 → 精確計算答案與中間值 → 渲染步驟 → 產生錯解與去重 → 隨機排列 → 回傳題目。

規則採後端白名單函式，不從資料庫內容直接 eval。分數用 Fraction 或明確有理數表示，符號答案採受限運算與正規化；只比較顯示字串不足以判斷數學等價。抽樣超過上限回傳可診斷錯誤，不無限重試。

現有前端持有 is_correct 並自行判分，適合展示但不適合可信的學習紀錄。第二階段新增 question_instance（instance_id、spec_id、spec_version、parameters JSON、建立/到期時間）及 instance_step_option（instance_id、step_order、opaque option_id、顯示內容、後端正誤）；前端只拿選項 ID，POST /api/steps/check 由後端判分。

再新增 game_session（session_id、目前 HP/MP/能力值、目前題目與步驟、狀態）與 answer_attempt（attempt_id、session_id、instance_id、step_order、option_id、is_correct、elapsed_ms、hint_count、hp_before/after、ability_before/after、request_id、answered_at）。request_id 在 session 內唯一，重送不得重複扣血；同一 session 鎖定或版本檢查避免並行作答。發布規格不得原地改動已產生題目的語義，instance 要保存足夠快照。

## 8. 驗收與合作交付

每個規格至少 100 組隨機參數，另含零值、負數、最小/最大值、分母、重根等邊界；由獨立計算或已知示例核對答案和每一步，不能只比較最後選項文字。檢查 LaTeX、無未替換標記、四個數學不等價選項與唯一正解。跨參數限制也要在提交答案驗證端重跑。

驗證兩步、三步、五步題；當前練習版最多四步，五步情境另建測試題。測試答錯扣 25 HP 並扣能力值、第四次歸零重生、答對換題、提示、逾時、缺題與 API 失敗。若當前 HP 已因前一題減少，跨題累積計算，不能保證每題都能錯四次。

schema/seed 要能在乾淨開發庫匯入；重複執行不能複製題目或覆蓋既有人工修改；migration 版本化。交付 .sql、規格目錄、來源清單、測試結果及設定範例。密碼只存在本機環境設定，不提交 GitHub。題目來源記錄自編/公開授權/參考改編與連結，未確認來源先不發布。
